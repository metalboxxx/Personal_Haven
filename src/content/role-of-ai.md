A model will help write much of this code. However, I believe the skill in the modern lanscape is the ability to determine clear goals, have a concrete vision and most importantly, enforcing the constraint of the project scope. 

LLMs are famously capable of thinking a thousand ideas without breaks rest and mental fatigue, given an unlimited ammount of time. For the same cost, LLM can spew out the quanitiy of ideas than any humans do, notwithstanding the quality. Humans thinking is narrowed minded and deeply provoked but LLMs is broad base [1][2]. With enough tries, you can actually do *anything*. Sound good! But it is a trap for any project.

When you can do *anything*, you lose scope, lose the purpose of the project. One might spend so much time on a feature that is essentially useless. One might focus on an element that actually distract users from the main point. So you need to implement *constraints*, which deeply connected to how clear your vision, your ambition is, the element that humans have. This idea is borrowed from Pixar methology. Suprising when the burden of technicality is lifted, many of the creative field principles can be applied.

So the workflow mainly I scope out what I want, my bussiness requirements and let them loose. As a junior developer, I don't have experience to go through pros and cons of the tech stack, so let the agents lists out them and let me choose. Setting up guard rails is good and which is the thing I do, but there are much things to said at the beginning. Only when do work progress where real drift occur. This is where having a clear goal shines. I found more value in iterating and micro adjusting the agents while they were generating. Furthermore, it is unusally hard to adjust when there too many things to change, like not understanding anything to ask a question, so I like generate code slowly while keeping a grand picture in mind.

There is still value in coding slow, there is value going through every code, Pr.Tao said here much better than I am, making analogy here for math. coding and math are strikingly similar, going through each line of code or each part of the equation to satisfyingly reach a conclusion. However, a huge demotivation looms when your colleuge finishes work 10 times faster than you, and just sitting there. Especially more demotivated when a genius experienced senior engineer you worked, answered with "Lets me just ask the chat bot" when I raised a rather diffifcult design question.

For me, I will try learning code that I presume I will look again in the future like python, model training, git,... or things related to security as properitary seldom unleash full cybersecurities of the model. Otherwise,  libraries, frameworkds, I pretend I am a project manager that cares about the outcome and the code is the black box that my engineers (here are ai agents) can understand. They can evaluate, choose, code whatever as long as meeting the functional and non functional requirements, and honestly, this defining action right here is actually a skill. I honestly doubt that any engineers even lead have every control over the code source, they will expertly trace back whenever there is a problem: the thing ai agents can already do.
